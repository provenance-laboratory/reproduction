# Pilot observation, 29 August 2026 — before any corpus or model exists

⚠️ **THIS IS NOT A MEASUREMENT.** It is a feasibility check run before phase 1, to confirm the
mechanism the pre-registration predicts actually exists on this hardware. It is recorded here,
dated, and separated from `PRE-REGISTRATION.md` so that nothing observed today can later be
presented as something planned yesterday.

None of the six pre-registered measurements has been taken. No corpus is fixed. No model exists.

---

## What was run

`numpy` 2.5.1 on `scipy-openblas` 0.3.33. A fixed-seed 512×512 float32 matrix product, iterated six
times, on one machine (Intel i5-1240P), varying only `OPENBLAS_NUM_THREADS`.

## What happened


**Four thread counts, four different results, bit for bit — on identical hardware, identical
inputs, identical library build.**

## Why this matters, and what it changes

The pre-registration's section 4 expects bit-identity to fail **across different hardware**, for
principled reasons including non-associative floating-point addition and reduction order. That
expectation stands. What this pilot shows is that the same mechanism bites **one machine below
itself**: thread count alone partitions the results.

⇒ **This sharpens the experiment rather than undermining it**, in three ways:

**1. Measurement 3 acquires a precondition.** *"Does bit-identity hold on identical hardware?"* now
has an obvious answer — only if thread count is pinned as well. Thread count therefore becomes part
of the published environment specification, not an incidental detail of the machine that ran it.

**2. A cleaner question becomes available.** With BLAS pinned to a single thread, the threading
source of reduction-order variation is removed, leaving instruction-set and kernel-selection
differences as the only candidates. So:

> **With threads pinned to one, does bit-identity hold ACROSS hardware?**

If it does, reproducible training is achievable under a stated constraint, and the cost of that
constraint is exactly what measurement 1 measures. If it does not, the failure is attributable to
microarchitecture rather than to scheduling, which is the deeper result.

**3. The testbed is the right one.** A pure-`numpy` pipeline has a dependency surface small enough
that a third party can actually run it, while still exercising the real mechanism — threaded BLAS
reduction order — that the prediction names. A CUDA pipeline would add non-deterministic atomics
and kernel autotuning, which are more sources of the same phenomenon and far fewer reproducers.

## ⛔ What is added to the protocol, before anything is trained

Committed now, in advance, as an amendment rather than a discovery:

- **`OPENBLAS_NUM_THREADS` is pinned and recorded** in every run and in the published environment
  digest. A run that does not record it is not admissible.
- **Every configuration is run at threads=1 and at threads=N**, so the threading contribution is
  separated from the hardware contribution rather than confounded with it.
- **A seventh measurement is added:** *divergence as a function of thread count on fixed hardware* —
  the magnitude, and whether it is monotone in thread count. Today's numbers suggest it may be, and
  suggesting is not showing.

⚠️ **Measurement 7 is added BEFORE the corpus exists**, which is the only reason it may be added at
all. A measurement invented after seeing a result is not a measurement, and the pre-registration
lists exactly six until this file amends it to seven.
